# M0 真实时间基线与 60 Hz 迁移影响

日期：2026-09-10。测量对象是提升前冻结的原始源码，使用其真实 `GameLoop` / `ScheduledTickScheduler`，没有修改生产时钟、运动数值或冷却。原始调度目标为 **16 ms / 62.5 Hz**。三轮各 250 个真实调度间隔测得 **62.339–62.432 Hz**。

## 输入、环境与测量边界

- 原始输入：`build/baseline-20260910/input/`，对应 M0 冻结点 `96422992f1dcb791bbc08aec3791ad63efb3e42a`。该输入已完成正式 Gradle 的 160 项测试和插件构建，见 [M0 记录](2026-09-10-baseline.md) 与 [构建恢复记录](2026-09-10-gradle-recovery.md)。
- 实际加载的 `Player.class` 和 `GameLoop.class` 均来自冻结副本的 `build/classes/java/main/`，测量日志记录了两类的 `CodeSource`，没有混入正在并行修改的生产类。
- Oracle JDK 17.0.12；IntelliJ IC 2023.2.2 的 API 类路径；Windows、AMD Ryzen 7 5800H。`java.awt.headless=true`，无窗口、无渲染、无敌人、无暂停、无 hitstop、无升级，平地 `groundY=480`，角色初始 `(100,450)`、高 30 px。机器未被设为独占负载，结果包含当时系统调度抖动。
- 多个独立 Player 在同一真实回调中执行各自固定输入；每轮 250 个间隔，重复三轮。所有位移、高度和事件 tick 在三轮中一致。
- 第 0 次回调是时间原点，输入已准备好但不推进角色；第 1 次回调才执行第 1 步。采样使用每次回调入口的 `System.nanoTime()`。不包含 JVM 启动、键盘设备、输入队列或显示延迟；属于模拟事件到回调时间的测量，不能解释为完整输入响应时间。
- 表中的“理论时间”为 `tick × 16 ms`；“实测范围”为三轮中同一事件的最小 / 最大真实时间。二者明确区分。

## 移动与一、二段跳

| 固定输入 / 事件 | 结果 | tick | 理论时间 | 三轮实测时间 |
| --- | --- | ---: | ---: | ---: |
| 持续向右 125 步 | 625 px | 125 | 2,000 ms | 1,999.786–2,012.564 ms |
| 持续向右 250 步 | 1,250 px | 250 | 4,000 ms | 4,004.388–4,010.316 ms |
| 一段跳到最高点 | 高 134.4 px | 22 | 352 ms | 354.530–363.101 ms |
| 一段跳回到地面 | y=450 | 44 | 704 ms | 704.664–717.388 ms |
| 较早二段跳：第 12 步更新前再次请求；最高点 | 总高 237.8 px | 33 | 528 ms | 527.941–537.502 ms |
| 同一较早二段跳落地 | y=450 | 62 | 992 ms | 999.181–1,005.742 ms |
| 第一段最高点后，第 23 步更新前再次请求；最高点 | 总高 268.6 px | 44 | 704 ms | 704.664–717.388 ms |
| 同一较晚二段跳落地 | y=450 | 75 | 1,200 ms | 1,200.310–1,208.119 ms |

理论步行速度为 **312.5 px/s**；250 步实测约 **311.70–312.16 px/s**。二段跳高度依赖触发时机，不能用一个没有输入时刻说明的“二跳高度”作为验收标准。

原始更新先积分重力和位置，再消费跳跃请求，因此请求进入首步时不会立即产生上移。第 23 步二跳在第一段顶点之后消费，重力积分已产生约 0.2 px 的下降；所以该协议测得 268.6 px，而不是把两个 134.4 px 直接相加。上述 tick 都从同一第 0 次回调开始计数。

## 冲刺、近战与状态持续时间

| 事件 | tick | 理论时间 | 三轮实测时间 |
| --- | ---: | ---: | ---: |
| 冲刺结束，位移 80 px | 8 | 128 ms | 128.562–137.320 ms |
| 冲刺后剩余冷却 | 45 | 720 ms 倒计时 | 此行是结束时读取的剩余 tick，不是独立测时 |
| 从首次冲刺到冷却归零，并在更新后接受再次冲刺 | 53 | 848 ms | 848.997–859.274 ms |
| 冲刺赋予的无敌状态结束 | 24 | 384 ms | 386.106–395.832 ms |
| 近战状态结束 | 8 | 128 ms | 128.562–137.320 ms |
| 从首次近战到更新后接受再次近战 | 30 | 480 ms | 480.424–490.300 ms |
| 近战期间一直按住射击，首次恢复射击 | 8 | 128 ms | 128.562–137.320 ms |
| 单独设置 60 tick 无敌，期间不冲刺 | 60 | 960 ms | 967.990–974.064 ms |
| 单独设置 180 tick 护盾 / SUDO，期间不冲刺 | 180 | 2,880 ms | 2,885.620–2,893.179 ms |

冲刺的 45 tick 冷却在 8 tick 冲刺**结束之后**才开始，因此完整再次可用周期是 53 tick。近战则在启动时同时设置 8 tick 动作和 30 tick 冷却，两个倒计时一起递减，因此再次可用是 30 tick，不是 38 tick。表中再次触发在更新后调用公开 API，只证明该状态已经可用，不声称键盘事件能在相同回调阶段立即重新触发。

原始 Player 的冲刺分支会提前 `return`，跳过其后统一递减的武器、SUDO、护盾、无敌、近战及近战冷却。实测冲刺结束时，无敌计数仍为初始的 16；经过额外 16 个正常步才到 0，所以总计 24 tick / 384 ms。迁移时若把所有倒计时统一移动到分支之前，会改变现有手感，即便常量完全不变。

本次只测量近战状态与射击解锁，没有用敌人碰撞测量逐步有效攻击判定数。角色更新会先递减近战计时，碰撞查询的前后顺序仍需单独纳入战斗验收。

## 射击节奏

固定为无升级、无 SUDO、无近战、无冲刺的持续射击，临时武器给 999 发弹药，避免回退核心武器。记录新增投射物的回调，统计相邻射击事件间隔。

| 原始武器 | 射击间隔 tick | 理论间隔 | 三轮平均实际间隔的范围 |
| --- | ---: | ---: | ---: |
| COMMIT | 18 | 288 ms | 287.619–288.412 ms |
| SPREAD | 26 | 416 ms | 415.450–416.596 ms |
| RAPID | 8 | 128 ms | 127.895–128.102 ms |
| HEAVY | 25 | 400 ms | 398.890–400.776 ms |
| FLAME | 12 | 192 ms | 191.951–192.288 ms |
| LASER | 30 | 480 ms | 479.876–480.721 ms |

全部武器首发均出现在第 1 步；这是本工具的输入协议，不表示武器自带 16 ms 蓄力。COMMIT / SPREAD 的真实冷却来自原始 `combat/WeaponCatalog.java:9,13` 的 18 / 26，不能误读旧 `model/WeaponType.java` 上遗留的 20 / 15。其余四种原始武器走旧分支，使用 `WeaponType` 的 8 / 25 / 12 / 30。

正在提升的当前版本已经改变部分武器行为，尤其 Refactor Beam 有 10 tick 蓄力（进化后 6 tick）和 20 tick 基础冷却。此表是原始比较基线，不能作为新武器实现的当前测量结果，也不能不检查递减顺序就把“蓄力 + 冷却”当成精确射击间隔。

## 直接改为 60 Hz 的影响

若只把模拟步长从 16 ms 改为约 16.6667 ms，其余 tick 常量和每步积分数值保持不变：

- 相同 tick 数的真实时长乘以 `62.5/60 = 25/24`，增加 **4.1667%**。例：单跳顶点 352→366.667 ms、落地 704→733.333 ms；冲刺 128→133.333 ms；再次冲刺 848→883.333 ms；近战再次可用 480→500 ms。
- 固定每步位移的真实速度乘以 `60/62.5 = 0.96`，降低 **4%**。步行 312.5→300 px/s，冲刺 625→600 px/s。
- 相同输入 tick 序列的离散空间轨迹仍相同，例如单跳高度仍为 134.4 px，但整条轨迹播放更慢。换成“同一真实时刻按二跳”的输入，则落在哪个 tick 可能不同，高度也会变。
- 每步 `GRAVITY=0.6` 对应的真实加速度从约 2,343.75 降为 2,160 px/s²，下降 **7.84%**；因此仅校正移动速度也不足以保持跳跃时序。
- 以 tick 计的子弹速度、敌人移动、预警、无敌、命中停顿、随机事件频率和动画都会受到同类影响，但这不等于已经完成各系统的实测。

若未来要求在 60 Hz 保持原有真实手感，需按“像素 / 秒、秒”转换整个运动与计时契约，并重新验证跳跃和碰撞离散误差；整数 tick 四舍五入会带来额外偏差，例如 18 个旧 tick 对应 17.28 个新 tick，8 个旧 tick 对应 7.68 个新 tick。仅改一个频率常量或统一取整不能保证等价。本轮没有实施任何转换。
